### 1. 总体结论

该文件是可读的 Windows 控制台原型，已经串起前台窗口采集、关键词分流、远程语义判断、分档对话、本地记录、有限状态落盘、Windows锁屏和终局动作。它适合作为规则原型和迁移参考，不宜直接充当 Windows GUI 与 Android 的共同运行核心。

主要原因是状态机、交互、网络、平台动作和文件操作集中在同一阻塞循环里；若干分支的实际语义与注释/产品宣称不一致；持久化不足以恢复正在进行的执行周期；正常配置变更、模型异常、检测失败均可能导致错误行为。无需添加反破解或成果审计才能修复这些问题。

### 3. 具体问题：阻断正式版发布的优先项

#### P1-01：模型输出格式错误时仍可能判为 ESCAPE

证据：294–297。JSON解析失败后，通过原文是否包含 `ESCAPE` 或 `WORK` 猜测结果，而且优先匹配 `ESCAPE`。例如无效JSON回复“这不应判为 ESCAPE”也会变成 ESCAPE。随后897–904直接转为DRIFT，进入升级逻辑。

修改：只有符合明确schema的枚举与字段才接受；解析失败、缺字段、多余非法结果或不可用统一返回UNKNOWN。UNKNOWN的具体显示策略可以配置，但不能静默转换成违约。AI输出应是建议，最终事件由确定性策略层在证据仍新鲜、当前周期仍一致时决定。

#### P1-02：缓存不包含目标或规则版本，修改主线后继续使用旧判定

证据：248缓存键仅为进程名和窗口标题；249–254只检查TTL；832–835允许每轮热加载新的目标和配置。

修改：缓存至少关联 cycle_id、goal_version、policy_version、模型/提示词版本、标准化后的观测摘要；主线变更使旧请求和旧缓存失效。设置容量上限与过期淘汰，避免每个浏览器标题无限累积。

#### P1-03：交互与网络阻塞监测，事实与措施可能过期

证据：230同步网络请求；386–394还会再请求生成质问；461、487、714均为无超时`input`；主循环947等待选择。用户不输入时，主循环不会继续采样或推进计时；用户在AI请求期间已经返回主线，程序仍可能根据请求前的窗口显示质问并接受触发锁屏的输入。953还把提问时间设置为网络与交互前的`now`。

修改：采集、策略、UI和AI任务解耦。模型请求携带cycle_id、observation_id、goal_version与截止时间；响应回来时重新确认仍适用。交互超时、被关闭、切换设备、系统休眠均是显式事件。是否因“没有回应”升级需要产品明确，不能把阻塞实现当作规则。

#### P1-04：选择分支无法正确实现三档状态

证据：978–983的BREATHE分支不更新`escalation_stage`，因此从第1档反复选喘息会一直停留在第1档；955–957的BACK在用户仅表示要返回时立即清档，绕过878–883声明的连续回主线确认；462–463的EOF也被当作BACK；465–470将第1/2档任意未知输入视作BACK。

修改：将“用户表达意图”“观察到主线”“持续达到降档阈值”“输入通道故障”区分为独立事件。BREATHE应按已批准策略更新档位及下一次核对条件；BACK是否直接降档由策略明确，若采用连续回归则先进入RETURN_PENDING。EOF/无效输入不得伪造用户选择。强硬档位与终局保留，只修正执行一致性。

#### P1-05：灰区中的合法主线活动永远不能按正常路径降档

证据：887–889先将`on_task_seconds`清零；897–902对WORK与UNKNOWN一并只清空漂移，不累积主线时间。只有离线关键词命中的ON_TASK在875–885积累主线和降档。因此在浏览器中持续做AI认为相关的活动，也无法满足同样的回归规则。

修改：WORK建议经确定策略接受后进入统一的“相关活动”计时路径；UNKNOWN保持未知，不能伪造为已回主线。观测分类与模型建议组合后只使用一套时间累计和降档规则。

#### P1-06：终局自删除按文件名前缀枚举，边界超过安装产物

证据：731–749。`self_destruct_armed`为真时，删除脚本目录下所有以 `iron_will_`、`test_judgment`、`test_escalation`、`probe_signals` 开头的条目。用户未来同前缀的设计文档、备份和无关文件也会进入候选；目录删除会失败形成部分删除。这不是正式Windows卸载流程；已打包的正在运行文件也可能不能这样删除。

修改：保留“可选终局后卸载”产品策略，但使用安装器拥有的精确文件清单和平台卸载机制；归档目录与安装目录分离。是否保留密钥、状态和记录由清晰的数据保留选项决定。终局功能测试只能调用假的动作适配器，不能在源码目录真实删除。原型默认保险分支仅打印列表（739–744），不能因此宣称正式卸载已实现。

#### P1-07：持久化不完整，终局不可恢复且可重复执行

证据：575默认状态只有date、oath_spent、lock_strikes；797–802的档位、上次选择、各计时和缓存仅存内存；805–807只在启动载入一次。第二次锁屏在934调用完成后才于935保存次数；第三次终局925之前没有保存终局状态；终局流程767–772也没有写入terminal_completed或phase。

影响：崩溃/重启会丢失档位与监督期；在复锁中中断可丢本轮次数；终局后再次启动还可以监督、再次归档。不是要求防破解，而是正常崩溃恢复与幂等性要求。

修改：采用可迁移的执行周期状态，至少持久化cycle_id、policy_version、phase、escalation_stage、previous_choice、oath_shown/spent语义、strike计数、监督期限及已完成动作ID。先事务性记录待执行动作，再执行平台动作、记录结果；恢复时按幂等规则处理，禁止重复删除/重复终局归档。

### 4. 其他必须修改或明确的行为

#### P2-01：日期重置与“执行周期”不兼容，现有日期逻辑自身也不一致

证据：559–575按本机日期判断；805仅启动时读取。长时间运行跨午夜不会自动重置；同样状态在午夜后重启却会清零。935和975还把当前日期直接写入旧内存状态。当前需求应改为显式执行周期，不把午夜或进程启动当周期边界。周期结束、暂停、恢复及新主线是否新周期须列为产品决策。

#### P2-02：不是实际时长计量，且把跨窗口时间归因给当前窗口

证据：877与889每轮加配置interval，而不是实际采样间隔；848、911、632–634使用墙钟；430声称当前窗口连续停留某时长。漂移可跨多个窗口累计，程序未追踪窗口切换时刻；API等待、input、额外sleep和调度延迟也不在计量内。

修改：单机经过时间使用单调时钟，明确休眠/锁屏/空闲/未知的计时规则；“连续偏离主线时长”与“当前窗口时长”分别累计、分别描述。持久化跨重启期限另用受限的墙钟时间与恢复规则。当前观察ON_TASK立即清空stray_seconds（876），是否必须持续回归才能清漂移应明确，不能仅靠含混注释。

#### P2-03：配置热更新不完整、无schema与边界校验

证据：783保存初始scfg；832–846重读部分字段，但860依旧读启动时scfg中的active_window_tracking。90–92不验证JSON；字典字段大多直接索引；169–185不统一关键字大小写且空字符串会匹配所有内容；max_stage、interval、阈值等无范围/类型约束。主循环只捕获KeyboardInterrupt（987），配置半写、字段缺失、IO错误可能直接退出。

修改：带版本的配置schema、一次性校验完整快照、失败保留上一份有效配置、事务发布新版本；界面展示当前生效版本。将空关键词、非正采样周期、非法档位与锁屏参数视为配置错误。热更新范围明确，不声称所有字段即时生效。

#### P2-04：窗口检测失败可能进入语义判定和处罚路径

证据：143–154失败返回unknown和空标题；198将其归为GRAY；累计阈值后896仍可请求语义判断。模型可能凭不足信息输出ESCAPE。

修改：明确OBSERVATION_UNAVAILABLE状态，采集失败不视作用户行为，不请求缺乏观测内容的相关性判断；保留诊断码与最近成功观测时间，恢复后重新计时。

#### P2-05：锁屏“尝试”被记成“成功”，复锁语义与主循环不同

证据：599–607返回成功与否，但631、642忽略；计数在920或972先发生；复锁637–639只用离线DRIFT，不复用主循环接受的灰区ESCAPE建议。监督期内部不接收最新配置或周期事件。

修改：统一动作结果协议（requested/succeeded/failed/unsupported）；操作失败不能记录为成功。复锁到底只针对明确本地红线，还是包含经过时效校验的灰区建议，需策略明确。保留Windows用户可解锁这一能力边界；不把它包装成定时不可解除的系统锁。

#### P2-06：所谓“唯一联网层”与代码不符，发送的数据超过标题

证据：205–234是远程DeepSeek接口；264–275向相关性模型发送当前主线、目标、灾难后果、进程与标题；314–394的质问生成另行联网，并发送麻烦、后果、誓言等字段。因此L3不是唯一联网用途。主循环L0 PRIVATE在868–872确实提前退出，可复用这一保护顺序；但两个联网函数本身没有统一的隐私出口检查。

修改：语义建议与人格生成设独立开关、权限和数据清单；相关性通常只需目标摘要与经处理的观测。统一出口执行隐私过滤与最小化，明确原话和私密困境是否允许发送。AI人格生成是否仍需保留，由用户确认；本审查不把全部AI移除。

#### P2-07：原话和事实约束只是提示词，没有输出校验

证据：393–394直接采用模型文本；377要求逐字引用但无字符串校验；330–374鼓励AI自由组织反问；405、409、451硬编码15分钟，而cooldown可配置；671硬编码“两次锁屏”，但阈值794/846可配置。模型或配置变化可能让台词编造时长、次数或原话。

修改：用户原话、次数、时长、选择记录作为不可改写槽位由应用拼接；人格只生成被允许的连接句。输出长度和控制字符限制、引文一致性校验、失败回退固定模板。若最终产品要求AI仅供语义建议，则人格部分改为已批准模板即可，不影响语义AI保留。

#### P2-08：大愿“只用一次”的实现需要定义清楚

证据：806、916–919描述当天一次；实际只有用户在最高档选LOCK，971才把oath_spent置真。最高档展示后选BACK，会在未来再次展示。区分oath_shown与oath_rejected；究竟展示一次还是拒绝后用尽，需要产品明确后写迁移规则。

#### P2-09：状态写入失败被吞掉，多个实例可能互相覆盖

证据：578–592固定`.tmp`文件名且异常全部忽略，无文件锁或单实例；559–574损坏状态直接当新状态。系统无法区分首次使用与记录损坏。

修改：单实例或事务数据库；错误可观测、保留最近有效快照；损坏进入恢复流程，不无声清零。运行状态放入用户数据目录，不能依赖安装/源码目录可写。

#### P2-10：不是纯导入模块，Windows GUI/无控制台启动会出问题

证据：39–49在导入时修改全局标准流；45在try之外调用`sys.stdin.isatty()`，当GUI运行环境的stdin为None时会直接失败；53–58导入Windows依赖；64–71绑定脚本所在目录；控制台清屏与input散布各功能中。1057的main保护确实避免导入时自动进入监测/锁屏，但不意味着导入完全无副作用。

修改：纯领域模块无平台/控制台副作用；CLI入口负责控制台设置；Windows采集与锁屏单独适配；GUI以事件调用核心；路径由平台数据目录注入。Android应原生实现能力适配，不尝试直接运行这段Windows循环。

#### P2-11：本地明文与文本输出需定义保留和显示边界

证据：95–102支持脚本旁明文密钥；499–552记录完整标题、理由、目标后果；647–684归档署名和自述；1016–1018的probe会打印PRIVATE标题。没有观察到加密存储、保留期限、脱敏导出和访问隔离实现。未发现真实Git上传实现；忏悔文字不能被误写成“已经公开发布”。

修改：密钥使用系统凭据存储；私密原文默认本地；诊断与导出使用独立隐私规则；记录保留、删除和归档由明确策略决定。窗口标题与模型文本作为不可信数据，限制控制字符并按目标渲染格式转义，避免终端控制序列或Markdown结构注入。

#### P2-12：文本相等校验不等于“逐字手打”

证据：714使用普通input并strip，718比较字符串；没有阻止粘贴或判别输入来源，也不记录完成事件。当前能证明的是去除首尾空白后文本相等。若保留手打仪式，应如实描述为确认文本或用GUI处理输入事件；不应为追求防绕过增加低层键盘钩子，且辅助输入兼容策略需要单独决定。

### 二、初始化程序实际行为

#### 2.1 路径与覆盖范围

- `iron_will_setup.py:22–24` 以脚本自身目录生成配置和归档路径，具有相对可移植性。
- `:134–142` 覆盖 `pain_vault` 的七个字段（`primary_goal`、`current_trouble`、`immediate_necessity`、`blocker`、`disaster_consequence`、`backup_plans`、`sacred_oath`），覆盖 `signature.user_signature`，更新 `profile.last_updated`。
- 其余字段随原字典重新序列化，现有 `judgment_config`、模型连接参数、隐私关键词和 `self_destruct_armed` 会被保留；程序没有把自毁开关改为真。
- `:134–142` 没有结构校验或缺省对象建立。非空但缺少 `pain_vault`、`signature` 或 `profile` 的配置会在用户回答完问题后报错；非字典根对象同样不受支持。
- `:29–36` 将文件不存在、权限错误、编码错误、JSON 错误统一吞掉；`:57–59` 统一报告基础配置不存在，排障信息不足。当前空配置不会被继续写入，但此函数不宜直接复用于自动修复逻辑。

#### 2.2 原子保存成立的范围

- `:47–52` 是同目录固定 `.tmp` 文件写入，再 `flush()`、`os.fsync()`，最后 `os.replace()`；配置替换本身具有原子替换的实现基础。
- 固定临时文件名没有进程间锁；两个初始化进程并行运行可能互相覆盖临时文件或导致替换失败。它也不能防止“加载旧配置—另一进程更新—整个旧字典写回”的更新丢失。
- `:144` 先提交配置，`:147–200` 后创建目录和直接写 Markdown 归档。这不是跨两个文件的事务：配置成功而归档失败时，状态已经改变，程序可能直接异常退出。
- `:150` 归档名只精确到秒；同一秒的两次归档可能撞名，`:199` 的 `w` 会覆盖旧归档。归档本身不使用原子替换。
- `.tmp` 在失败时可能保留，包含与配置同等敏感的个人内容。原子替换不等同于加密、访问隔离或整个契约事务的持久性保证。

#### 2.3 与当前产品或数据语义不一致之处

- `:110–112` 根据输入是否包含 `无`、`没`、`no` 等子串，把用户填写的 `backup_plans` 改写为固定文本。一般句子包含这些字也可能被改写；这不是忠实保存用户选择。迁移时应保留原有已存值，不推测改写前内容。
- `:120–122` 用字符长度判断大愿是否合格；这只验证长度，不验证身份标准。`:129–131` 只验证署名非空。
- `:140–142` 改了大愿和用户署名，但未更新 `signature.signed_at`、`author_name`、`executor_name`、`model_at_signing` 等元数据。旧元数据会与新契约共存；需定义这些字段分别指“历史作者”“本次签署”还是“当前版本”。
- `:189–196` 的归档执行条款是硬编码文本，未从有效配置/状态机生成。`:192` 同一句既说前三档都有出口，又说大愿档没有出口；`:193` 写 5/15/45 分钟，而当前产品口径为 5/15 分钟后第三次终局。归档不能视为运行行为的可靠规范。

### 五、建议的迁移实施规则（待主技术规范定版）

1. 先为新配置确定 `schema_version` 和严格类型/范围校验；读入失败应显示具体诊断且不改旧文件。不要调用旧程序来“试运行兼容性”。

3. 旧 `blacklisted_keywords` 到新规则是语义迁移，不是数组复制：进程、标题、主线、中性容器和隐私作用域需要区分；不确定分类应留下待确认项。当前实例已经是拆分结构，无需回填旧字段。
4. 将现有自毁关闭值、隐私设置、忏悔模板和终局选择作为显式保留项。新增平台若不支持原动作，必须显示能力差异；不能把 Android 的其他限制能力冒充桌面锁屏或同等卸载。

7. 迁移验证只对脱敏副本做解析、字段检查、往返序列化、原子写故障注入和恢复检查；不执行真实锁屏、自毁、卸载或对外发送。
